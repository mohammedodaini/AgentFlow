# ADR-0003: UUIDv7 primary keys, generated in the application

- **Status:** accepted
- **Date:** 2026-08-12
- **Milestone:** M2

## Context

Every table needs a primary key, and the choice is close to irreversible: the
key type appears in every foreign key, every index, every URL and every log
line. Changing it later means rewriting the whole schema.

Three properties matter for AgentFlow:

1. **Ids appear in URLs** (`/documents/{id}`). A sequential integer tells any
   customer how many documents the entire system holds, and lets them probe
   `id - 1` for someone else's row.
2. **Ids are generated by several writers.** The API, arq workers and agent
   tools all insert rows. Anything that must ask one central allocator for the
   next value becomes a coordination point.
3. **Insert throughput matters.** `document_chunks` gets thousands of rows per
   uploaded document, and `agent_steps` grows on every agent run.

## Decision

`UUIDPrimaryKeyMixin` in `app/models/base.py` gives every table:

```python
id: Mapped[uuid.UUID] = mapped_column(primary_key=True, default=uuid7)
```

`uuid7()` lives in `app/core/ids.py` and implements RFC 9562 §5.7: a 48-bit
millisecond timestamp, then version and variant bits, then 74 bits from a
CSPRNG.

## Consequences

**Good.** Ids carry no sequence information, so they are safe in URLs. Any
process can mint one without coordination. Because the timestamp leads, new
rows append to the right edge of the primary-key B-tree instead of scattering
across it: the property random UUIDv4 keys lack, and the reason v4-keyed
tables need far more vacuuming than their row counts suggest. `ORDER BY id` is
`ORDER BY created_at` for free, and a pagination cursor can just be the id.

**Bad.** 16 bytes rather than 8, in every table and every index. At AgentFlow's
scale that is a rounding error; at a billion rows it would deserve a second
look. A v7 id also leaks its creation time to anyone holding it, fine for
organizations and documents, wrong for anything secret. Password-reset tokens
and similar use `secrets.token_urlsafe`, which is a different tool for a
different job.

**Also bad, and worth knowing:** `default=` is a *column* default, so the id is
assigned when SQLAlchemy builds the INSERT, not when you call the constructor.
`Organization(...).id` is `None` until `flush()`. This surprised us during M2
and is now pinned by a test.

## Alternatives rejected

**`bigserial`.** Smallest and fastest, and genuinely the right default for an
internal system. Rejected on property 1: sequential ids in a multi-tenant
product disclose volume and invite enumeration. Adding a public-facing second
identifier to every table costs more than 8 bytes a row.

**UUIDv4.** Same opacity, no ordering. Rejected on property 3: random keys
fragment the primary index, which is precisely the cost v7 was designed to
remove.

**ULID.** Time-ordered like v7, but a 26-character string with no native
Postgres type: meaning either a `char(26)` column or an extension, plus
conversion at every boundary. v7 is a plain `uuid` column that psql, pgAdmin
and every driver already understand.

**The `uuid-utils` or `uuid6` package.** A dependency, forever, for ten lines
of bit-packing against a stable RFC. Rejected: the implementation is smaller
than the code needed to justify the dependency, and it disappears entirely when
this project moves to Python 3.14, where `uuid.uuid7()` is standard library.

**Database-side generation** (`gen_random_uuid()`, or Postgres 18's
`uuidv7()`). Would make the id unavailable until after the INSERT returns, and
would pin us to Postgres 18 for a function we can write in ten lines.
